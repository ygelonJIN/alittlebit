## 3. 竞品与市场分析
- 市场现状：现有桌面自动化工具存在明显断层——传统 RPA（UiPath、Automation Anywhere、Blue Prism）规则驱动，UI 变化即失效；轻量 RPA（UI.Vision、OpenRPA、SikuliX）单层匹配，无降级策略；AI 工作流工具（Dify、Coze、Langflow）只处理文本/API，不碰桌面 GUI；Computer Use 类方案（Claude Computer Use、Open Interpreter）纯云端，慢且贵。低代码平台（n8n、Node-RED、ToolJet）不做桌面自动化。**4 级级联策略栈架构是市场空白。**
- 竞品对比：
  - 维度：本方案 vs 传统 RPA（UiPath/Automation Anywhere）vs 轻量 RPA（UI.Vision/SikuliX）vs AI 工作流（Dify/Coze/Langflow）vs Computer Use（Claude Computer Use/Open Interpreter）vs 低代码（n8n/Node-RED）
  - 核心机制：本方案采用 5 层降级策略栈（坐标回放→模板匹配→YOLO→OCR→云端 API），每个节点独立配置级联顺序和置信度阈值；传统 RPA 规则驱动无 AI 兜底；轻量 RPA 单层 CV 匹配；AI 工作流仅文本/API 编排；Computer Use 纯云端多模态推理；低代码不涉及桌面 GUI 自动化
  - 优势/劣势：本方案本地优先省成本省 token、多层降级高可靠、可视化无代码；劣势是用户需自行标注训练数据和调参。传统 RPA 成熟生态但无 AI 级联兜底。轻量 RPA 轻量简单但匹配可靠性差。AI 工作流生态丰富但不碰桌面。Computer Use 最智能但最慢最贵（2-5 秒/次）。低代码灵活但不支持桌面操作

## 6. 技术架构与技术选型
### 6.1 核心架构
可视化画布（React Flow）产出节点+连线的管线 JSON，通过 Electron 的 child_process 传递给 Python 执行引擎。执行引擎解析 DAG → 拓扑排序 → 逐个节点执行 → 每节点内按用户配置的策略栈级联执行 → 每步留痕截图+结果验证 → 实时通过 stdout JSON 回传进度到画布更新调试面板。

节点类型包括：鼠标操作（点击/拖拽/输入/滚动）、键盘操作、截图、等待（延时/条件等待）、判断（if/else）、循环。每个「点击目标」节点内可独立配置 5 道降级策略，支持逐层启用/禁用、置信度阈值设置（滑块 0-100%，默认 60%）、超时策略。节点内策略栈支持级联模式（按顺序逐个执行）和并行模式（同时执行取最高置信度）。

### 6.2 技术选型
- 模块：桌面壳
  - 选型方案：Electron (MIT)
  - 选型理由：桌面工具链统治地位（Cursor/VS Code/Discord 均采用），React Flow 已跑通，参考产品 Open-Adapt、Rivet 均采用。包体积约 150MB，自动化用户可接受
- 模块：工作流画布
  - 选型方案：React Flow (@xyflow/react, MIT)
  - 选型理由：自定义节点渲染任意 React 组件（策略栈配置面板嵌入节点），内置拖拽/缩放/连线/撤销/序列化，26k+ star，Stripe 等生产级使用
- 模块：前端框架
  - 选型方案：React + TypeScript
  - 选型理由：与 React Flow 生态一致
- 模块：键鼠控制 + 截图
  - 选型方案：PyAutoGUI + mss
  - 选型理由：Python 统一键鼠+截图+CV+YOLO+API，零跨进程开销。mss 截图速度是 PyAutoGUI 内置的 10 倍，numpy 直喂 OpenCV。协议 BSD-3 + MIT
- 模块：图像模板匹配（策略 2）
  - 选型方案：OpenCV (Apache 2.0)
  - 选型理由：Python 生态唯一图像匹配标准库，支持三层子降级——matchTemplate（<10ms，同机器同分辨率）→ SIFT/ORB+FLANN（<50ms，抗缩放旋转）→ Canny 边缘+matchShapes（<30ms，抗主题色切换）
- 模块：YOLO 推理（策略 3）
  - 选型方案：YOLOX (Apache 2.0)
  - 选型理由：唯一 Apache 2.0 协议的成熟 YOLO 实现，可商用闭源。Ultralytics 为 AGPL，分发产品必须开源，不可接受。用户自行截图标注+自定义训练参数
- 模块：OCR 文字定位（策略 4）
  - 选型方案：macOS Vision / Windows OCR / Tesseract / PaddleOCR 全保留，用户按需选择
  - 选型理由：系统 OCR（Vision/Windows OCR）零成本即时加载；Tesseract 拉丁语系最优（15MB/50ms）；PaddleOCR 中文最强跨平台兜底（100MB/80-150ms）。产品内置「系统 OCR（自动）」模式——Mac 走 Vision、Win 走 Windows OCR，不够再切 PaddleOCR
- 模块：多模态 API（策略 5）
  - 选型方案：用户自定义 HTTP endpoint + API key，产品只负责截图→发请求→解析返回坐标
  - 选型理由：不做预设，支持压缩截图、区域截图、坐标缓存（高亮提示非自动复用）、级联多 API（多数投票+优先级排序）
- 模块：执行引擎
  - 选型方案：自研 DAG 调度器（Python）
  - 选型理由：拓扑排序→顺序执行→策略级联→结果验证，通过 stdout 每行一个 JSON 与 Electron 通信，无额外依赖
## 7. 技术难点与解决方案
- 难点/风险点：截图匹配跨机器可靠性
  - 瓶颈分析：matchTemplate 像素逐点比对，系统分辨率（1080p→4K）、系统缩放（100%→150%）、应用内缩放三层叠加导致同一按钮在不同环境像素尺寸完全不同，模板 100×100 对截图 200×200 直接返回 0.1
  - 应对策略/降级方案：多模板库方案。用户为不同环境录不同模板，产品记录系统分辨率/缩放比例/目标应用标签，匹配时逐个试取最高分。不自动生成多分辨率模板，用户自行管理

- 难点/风险点：YOLO 训练数据获取
  - 瓶颈分析：COCO 数据集无 UI 按钮类别，不同应用按钮视觉差异大（Chrome 蓝色圆角 ≠ Excel 灰色工具栏 ≠ 游戏木纹按钮）
  - 应对策略/降级方案：用户自行截图标注 + 全参数开放（epochs/batch size/数据增强强度/学习率等），覆盖 3-5 个常用应用精度可达 95%+，换新应用补标几张微调即可。Phase 4 内嵌自建标注工具（截图框选→标签→导出 YOLOX 格式）

- 难点/风险点：云端多模态 API 延迟和成本
  - 瓶颈分析：1920×1080 截图转 base64 约 2-8MB，网络+推理 2-5 秒，高频场景不可接受
  - 应对策略/降级方案：四重优化——①压缩截图（缩放+JPEG 压缩，参数用户可调）②区域截图（用户框选区域，不截全屏）③坐标缓存（云端命中坐标存下来，下次高亮提示用户决定是否跳过 API）④级联 API（多 API 同时发请求，多数投票+优先级排序，用户可选手动模式看所有结果自选）

- 难点/风险点：跨平台键鼠注入
  - 瓶颈分析：不同系统对模拟键鼠有安全限制，是权限问题非技术问题。PyAutoGUI 底层已封装
  - 应对策略/降级方案：macOS 用 CGEvent（需辅助功能权限，首次启动引导设置）；Windows 用 SendInput（不要以管理员权限运行，避免 UIPI 阻断）；Linux 用 xdotool/ydotool（自动检测 X11/Wayland 切换）。杀毒误报（截屏+模拟输入=行为特征高危）引导用户将应用加入白名单

- 难点/风险点：工作流调试体验
  - 瓶颈分析：策略匹配成功不代表操作正确，第 3 步误点击到第 8 步才暴露，追第 8 步没用
  - 应对策略/降级方案：每步留痕+结果验证。执行前截图→执行策略→执行后截图→两张图对比高亮变化区域。用户可设预期验证（如 OCR 读到「提交成功」），验证失败暂停管线+展开调试面板回放所有步骤的截图/匹配位置/置信度/变化对比

- 难点/风险点：降级阈值调优
  - 瓶颈分析：每层匹配返回数值，无通用最优阈值，阈值靠经验但用户不知道从哪开始
  - 应对策略/降级方案：纯手动滑块 0-100%，默认 60%。不给推荐、不给数据、不给自动。默认 60% 保证忘了调也能跑，用户按需调松调严
