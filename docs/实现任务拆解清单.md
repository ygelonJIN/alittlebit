# 实现任务拆解清单

## 1. 文档目的

本文档把当前项目的改造工作拆成可以直接执行的任务包，适合交给低能力模型、外包执行者或分阶段开发者逐步完成。它的目标是让每一步都明确：改什么、为什么改、怎么验收、什么时候算完成。

---

## 2. 执行总原则

1. 一次只做一个任务包。
2. 先改骨架，再改细节。
3. 先修编辑器，再修 Chat，再做数据化，再做组件化。
4. 不确定是否要删的内容先保留。
5. 每个任务包必须有明确完成标准。
6. 改动必须可回溯。
7. 不允许跳过任务顺序。

---

## 3. 任务包总览

| 任务包 | 目标 | 难度 | 是否优先 |
|---|---|---:|---|
| A | 页面骨架统一 | 中 | 是 |
| B | 编辑器重构 | 高 | 是 |
| C | Chat 面板重构 | 中 | 是 |
| D | 数据模型接入 | 中 | 是 |
| E | 组件拆分 | 中 | 是 |
| F | 版本与差异治理落地 | 高 | 视进度 |
| G | 文档与目录落地 | 低 | 是 |
| H | VS Code 源码借鉴整理 | 中 | 视进度 |

---

## 4. 任务包 A：页面骨架统一

### 4.1 目标

把页面先变成一个统一的工作台，而不是多个独立区域拼在一起。

### 4.2 要做的事

- 统一顶部版本栏样式
- 统一左侧文件栏样式
- 统一中间编辑区样式
- 统一右侧 Chat 面板样式
- 抽取公共颜色、边框、圆角、间距变量
- 统一各区域标题行高度

### 4.3 不要做的事

- 不要改编辑器行级结构
- 不要做版本治理逻辑
- 不要重写数据模型
- 不要删未来可能会用的模块

### 4.4 完成标准

- 页面看起来像一个整体
- 三栏或四栏节奏一致
- 没有明显样式割裂
- 公共变量已抽出

---

## 5. 任务包 B：编辑器重构

### 5.1 目标

让中间编辑器真正具备稳定的当前行高亮、行号对齐和滚动稳定性。

### 5.2 要做的事

- 将当前行高亮从浮层改为行级绑定
- 行号和文本一一对应
- 修复滚动后高亮丢失问题
- 统一字号、行高、padding
- 让编辑器更接近真实 IDE 行为

### 5.3 不要做的事

- 不要把 Chat 一起重构
- 不要顺手改版本系统
- 不要用绝对定位浮层伪造选中态
- 不要一次性引入复杂语法高亮系统

### 5.4 完成标准

- 当前行高亮稳定
- 行号与文本对齐
- 滚动后状态不丢
- 编辑器像真正的 Markdown 编辑区

---

## 6. 任务包 C：Chat 面板重构

### 6.1 目标

把右侧 Chat 面板做成克制的协作面板，而不是普通聊天 App。

### 6.2 要做的事

- 统一消息气泡风格
- 加入上下文显示区
- 统一输入区样式
- 统一发送按钮样式
- 让消息流更适合文档协作

### 6.3 不要做的事

- 不要让它比编辑器更抢眼
- 不要引入社交聊天式视觉
- 不要在没有上下文的情况下乱写消息模型

### 6.4 完成标准

- Chat 面板克制统一
- 输入区清楚
- 上下文明确
- 能服务于文档推进

---

## 7. 任务包 D：数据模型接入

### 7.1 目标

把版本、文件、编辑器行、消息等内容从静态硬编码转为数据驱动。

### 7.2 要做的事

- 建立版本列表数据
- 建立文件树数据
- 建立编辑器行数据
- 建立 Chat 消息数据
- 建立当前选中状态

### 7.3 不要做的事

- 不要在组件里继续堆静态文本
- 不要让 UI 直接决定业务状态
- 不要把还没定下来的字段写死成最终版

### 7.4 完成标准

- 页面内容可由数据渲染
- 核心模块都能从状态对象中取值
- 后续接真实状态管理不需要大改结构

---

## 8. 任务包 E：组件拆分

### 8.1 目标

把页面拆成职责单一、便于维护的组件。

### 8.2 要做的事

- 拆出 `TopVersionBar`
- 拆出 `FileExplorer`
- 拆出 `MarkdownEditor`
- 拆出 `ChatPanel`
- 拆出 `StatusBar`

### 8.3 不要做的事

- 不要把所有逻辑塞进一个大文件
- 不要为了拆而拆
- 不要让组件之间互相引用太深

### 8.4 完成标准

- 每个组件职责清楚
- 结构清晰
- 后续可以单独替换任意组件

---

## 9. 任务包 F：版本与差异治理落地

### 9.1 目标

让版本、差异、确认、冻结、归档真正进入可执行状态。

### 9.2 要做的事

- 建立版本状态字段
- 建立差异文件结构
- 建立确认记录结构
- 建立冻结摘要结构
- 建立归档目录规则

### 9.3 不要做的事

- 不要覆盖历史版本
- 不要把差异文件当正文
- 不要把归档区当工作区

### 9.4 完成标准

- 版本变化有记录
- 差异可回看
- 冻结可追踪
- 归档后只读

---

## 10. 任务包 G：文档与目录落地

### 10.1 目标

让现有文档变成一个清晰、可持续扩展的文档体系。

### 10.2 要做的事

- 统一文档命名
- 统一目录职责
- 统一版本目录规则
- 统一日志、差异、归档位置

### 10.3 不要做的事

- 不要乱改文件名
- 不要把正文和摘要混在一起
- 不要把所有内容塞到一个文件里

### 10.4 完成标准

- 文档能快速定位
- 目录职责清楚
- 新文档接入时不容易乱

---

## 11. 任务包 H：VS Code 源码借鉴整理

### 11.1 目标

把 `vscode-main` 里的可借鉴部分整理成可执行参考，而不是直接复制。

### 11.2 要做的事

- 识别布局骨架参考
- 识别 Explorer 参考
- 识别 Editor 参考
- 识别 Panel 参考
- 识别 Tab/状态栏参考

### 11.3 不要做的事

- 不要直接整包搬运
- 不要试图一次性实现 VS Code 全量能力
- 不要把复杂功能加入当前 MVP

### 11.4 完成标准

- 形成可执行的借鉴清单
- 形成“哪些借、哪些不借、哪些改造后保留”的记录

---

## 12. 推荐执行顺序

建议严格按以下顺序执行：

1. 任务包 G：文档与目录落地
2. 任务包 A：页面骨架统一
3. 任务包 B：编辑器重构
4. 任务包 C：Chat 面板重构
5. 任务包 D：数据模型接入
6. 任务包 E：组件拆分
7. 任务包 F：版本与差异治理落地
8. 任务包 H：VS Code 源码借鉴整理

如果资源有限，最少先完成 A + B + C + G。

---

## 13. 低能力模型执行方式

如果交给低能力模型，必须做到以下几点：

- 一次只发一个任务包
- 每个任务包只给一个明确目标
- 只允许改指定文件
- 不允许擅自扩展范围
- 完成后必须输出变更摘要和未完成项

---

## 14. 每个任务包统一交付格式

每个任务包完成后，必须交付：

- 目标
- 修改文件
- 修改内容
- 完成标准
- 风险点
- 未完成项

---

## 15. 结论

这份拆解清单的意义在于：

- 让复杂改造变成一组可执行任务
- 让低能力模型也能按步骤推进
- 让你能清楚知道每一步改到了哪里
- 让整个项目不会在中途失控
