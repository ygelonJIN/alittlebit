---

## 0. 先给结论

这套参考项目本质上不是一个“PRD 提示词仓库”，而是一套 **PRD 驱动的软件工程流水线**。

它把软件开发拆成如下阶段：

1. **从模糊想法生成 PRD**
2. **对 PRD 做完整性/可实施性验证**
3. **从 PRD 提取 Feature 列表**
4. **从 PRD + Features 生成 Rules**
5. **从 PRD + Features + Rules 拆 RFCs**
6. **基于 RFC 实施**
7. **基于 RFC + Rules 做 Code Review**
8. **基于 Features + RFC 生成测试策略**
9. **在需求变化时做 Change Management**

它的真正目标不是“问问题”，而是：

> **把产品想法变成结构化、可审查、可实施、可回溯的软件工程资产链。**

## 2. 这套工作流的核心哲学

### 2.1 不是“聊天”，而是“产物驱动”

这套项目的所有 prompt 都有一个共同点：

- 输入是某个阶段的文档或上下文
- 输出必须是某个明确工件
- 工件往往是 Markdown 文件
- 下游 prompt 默认上游工件已经存在

这意味着它把 AI 使用方式从“随便问答”变成“按照文档链条逐步推进”。

### 2.2 每一层都在做“语义收敛”

- PRD 层：把“想法”收敛成“产品需求”
- Feature 层：把“产品需求”收敛成“可实现功能”
- Rule 层：把“可实现功能”收敛成“开发标准”
- RFC 层：把“开发标准”收敛成“实现单元”
- Implementation 层：把“实现单元”收敛成“代码任务”

### 2.3 它特别重视依赖顺序

尤其是 `prd-to-rfcs-prompt.md`，明确要求：

- RFC 必须严格按顺序执行
- 前置 RFC 完成后，后置 RFC 才能开始
- 不允许并行实现

这说明它的设计目标是**降低 AI 失控概率**，不是追求一次性自动化所有事情。

### 2.4 它的产品观

这套工作流默认一个前提：

> 一个好项目，不是“AI 直接写代码”，而是先把需求、规则、依赖、实现边界说清楚。

这也是它为什么不断强调 PRD 的完整性。

## 3. 从“按什么目标问”来理解整套系统

你之前问过“它到底按什么目标问”。在这套参考里，答案不是单一目标，而是分层目标。

### 3.1 PRD 生成阶段问什么

问的是：
- 这个产品是什么
- 为什么存在
- 给谁用
- 解决什么问题
- 成功怎么衡量
- 边界在哪里
- 首发范围是什么

### 3.2 PRD 验证阶段问什么

问的是：
- 这份 PRD 是否缺关键项
- 是否可实施
- 是否存在歧义
- 是否有遗漏的技术/商业/合规问题

### 3.3 Features 阶段问什么

问的是：
- 需求里有哪些功能点
- 哪些是核心功能
- 哪些可以延期
- 每个功能的验收标准是什么

### 3.4 Rules 阶段问什么

问的是：
- 开发要遵守什么技术边界
- 应该采用哪些技术栈
- 代码结构怎么组织
- 状态、API、测试、安全、性能分别怎么约束

### 3.5 RFC 阶段问什么

问的是：
- 怎么拆实现单元
- 先做什么后做什么
- 每个实现块的依赖是什么
- 每个实现块的接口和验收标准是什么

### 3.6 实施阶段问什么

问的是：
- 当前 RFC 怎么落地
- 改哪些文件
- 先做规划还是直接改代码
- 有没有风险/取舍/替代方案

## 5.1 `interactive-prd-creation-prompt.md`

### 5.1.1 这个 prompt 的角色

这是整个工作流的起点。

它要做的不是“随便聊产品”，而是：

> 把一个非常模糊的产品想法，问成一份完整、结构化、可落地的 PRD。

### 5.1.2 它要求的 PRD 结构

它明确要求 PRD 包含：

- Overview
- Goals and Objectives
- Scope
- User Personas or Target Audience
- Functional Requirements
- Non-Functional Requirements
- User Journeys
- Success Metrics
- Timeline
- Open Questions / Assumptions

这说明它对 PRD 的理解是非常标准化的，不只是“写个需求简介”。

### 5.1.3 它的提问策略

#### 规则 1：分批问
- 一次问 3 到 5 个问题
- 不要一股脑把所有问题丢出来

#### 规则 2：先广后窄
- 先问目标、用户、场景、价值
- 再问功能、边界、约束、实现考虑

#### 规则 3：分组相关问题
- 不要把无关的问题混在一起
- 让用户更容易回答

#### 规则 4：根据回答调整
- 不是固定问卷
- 会根据前面答案动态改变下一批问题

#### 规则 5：关键问题优先
- 产品愿景
- 用户需要
- 核心功能
- 商业目标
- 实现考虑

### 5.1.4 它的隐含假设

它默认：

- 用户一开始的想法很模糊
- 不能直接写 PRD
- 需要通过引导式对话补齐信息
- PRD 是最终可存档、可传递的工件

### 5.1.5 它的输出目标

最终必须产出 `PRD.md`。

### 5.1.6 这一 prompt 的价值

它决定你能不能从“想法”进入“产品定义”。

如果这一层问得好，后续所有步骤都会顺；如果这一层问偏，后面 Features/Rules/RFC 也都会偏。

## 5.2 `prd-comprehensive-verification-prompt.md`

### 5.2.1 这个 prompt 的角色

它是 PRD 的“审校器”。

### 5.2.2 它不是继续建 PRD，而是检查 PRD

这点很重要。它的目标不是再问“产品是什么”，而是识别 PRD 的：

- 缺失项
- 模糊项
- 不可实施项
- 顺序问题
- 优先级问题

### 5.2.3 它检查的四个维度

#### A. Product Fundamentals
- 产品愿景
- 问题陈述
- 目标用户
- 成功标准
- 范围边界

#### B. Technical Requirements
- 技术约束
- 集成需求
- 安全/性能/扩展性
- 基础设施

#### C. Business Considerations
- 时间线
- 预算
- 法规
- 商业模式

#### D. Implementation Factors
- 依赖
- 团队能力
- 测试与部署需求

### 5.2.4 它的输出包含什么

- Summary of Findings
- Specific Recommendations
- Improved PRD
- Quality Assessment

### 5.2.5 这个 prompt 的本质

它不是“重新写 PRD”，而是：

> 用审查视角，让 PRD 变成足够可实施的版本。

### 5.2.6 为什么这很关键

很多 AI 生成的 PRD 最大的问题不是“没有内容”，而是：

- 结构有了，缺口没补齐
- 词写得很像，实际不能落地

这个 prompt 的存在就是为了防止这种情况。

## 5.3 `prd-to-features-prompt.md`

### 5.3.1 这个 prompt 的角色

它负责把 PRD 变成 FEATURES.md。

### 5.3.2 它做的不是“重新解释 PRD”

而是从 PRD 中抽取：

- 显性功能
- 隐性功能
- 依赖功能
- 可延期功能

### 5.3.3 它的四大任务

#### 任务 1：Feature Identification and Categorization
- 提取每个功能点
- 给功能编号（F1、F2、F3）
- 按类别分组
- 区分核心功能和增强功能
- 必要时关联 persona

#### 任务 2：Prioritization
- 使用 MoSCoW
- Must have / Should have / Could have / Won't have
- 结合依赖关系排序

#### 任务 3：Feature Detailing
- 功能描述
- 验收标准
- 技术约束
- 边界情况

#### 任务 4：Implementation Complexity
- Low / Medium / High
- 标出第三方集成或技术挑战

### 5.3.4 它真正做的事

它把 PRD 中的“自然语言需求”变成“研发可排期的功能单元”。

### 5.3.5 它的输出标准

最终要产出一个 Features 文档，并附总结视图，比如按优先级和类别统计数量。

### 5.3.6 这一步的意义

这是第一次把“产品语言”转换成“工程任务语言”。

## 5.4 `prd-to-rules-prompt.md`

### 5.4.1 这个 prompt 的角色

它生成 `RULES.md`，是开发约束与标准文档。

### 5.4.2 它的输入

- PRD
- Features

### 5.4.3 它的职责

#### 1. 定义技术栈
- 基础技术
- 版本偏好
- 必要工具/库

#### 2. 定义技术偏好
- 命名规范
- 文件组织
- 架构模式
- 状态管理
- API 交互
- 性能优化
- 安全实践

#### 3. 定义开发标准
- 测试要求
- 错误处理
- 日志
- 可访问性
- 响应式要求

#### 4. 定义实施优先级
- 核心功能 vs 增强功能
- 分阶段实施
- 质量阈值

#### 5. 定义通用规则
- 如何处理不确定性
- 完整性要求
- 不允许 TODO / 占位符

### 5.4.4 它的核心价值

`RULES.md` 相当于：

> 这项目怎么做、怎么写代码、怎么保持一致性的“宪法”。

### 5.4.5 为什么这一步重要

如果没有 Rules，后面的 RFC 和实现就会失去统一标准，AI 会在细节上自由发挥，最终导致风格混乱、架构不一致、实现质量不稳。

## 5.5 `prd-to-rfcs-prompt.md`

### 5.5.1 这个 prompt 的角色

这是把产品需求转成工程实施单元的关键阶段。

### 5.5.2 它的核心要求

#### 1. 严格顺序
- RFC 必须有依赖顺序
- 后一个 RFC 依赖前一个 RFC 的产出
- 不允许并行实施

#### 2. 图结构依赖
- 要分析 feature dependency graph
- 识别 critical path
- 确定 foundation components

#### 3. 合理分组
- 每个 RFC 代表一个 cohesive unit of work
- 不能太碎，也不能太大

### 5.5.3 每个 RFC 需要包含

- 唯一 ID
- 总结
- 覆盖的 features/requirements
- 技术方案
- 前置与后续依赖
- 复杂度评估
- 验收标准
- API contracts
- 数据模型/数据库变更
- 文件结构
- 关键算法或 UI 规格
- 状态管理
- API 集成
- 错误处理
- 测试策略

### 5.5.4 它为什么要求这么细

因为 RFC 已经不是“需求说明”，而是**可执行的工程说明书**。

### 5.5.5 它的深层意义

它把“项目拆分”变成“严格可依赖的施工图”。

## 5.6 `implementation-prompt-template.md`

### 5.6.1 它的角色

这是实施阶段的模板，不是一次性实现某个具体项目，而是给每个 RFC 提供统一实现方式。

### 5.6.2 它强调“两阶段”

#### Phase 1: Planning
- 分析需求
- 列出文件变更
- 提出设计方案
- 等待批准

#### Phase 2: Implementation
- 在批准后才动手
- 分段实施
- 复杂部分要解释
- 自检后交付

### 5.6.3 它强调什么

- 先计划，后写代码
- 不要绕过设计
- 不要随便打补丁式修复
- 改进已有组件优于重复造轮子

### 5.6.4 它的价值

它把“AI 直接修改代码”的风险降到最低，强制 AI 先做方案评估。

- Findings

- Improvement Suggestions

### 5.7.5 它的意义

把“代码评审”标准化，让审查不只是主观感觉，而是可复用的检查清单。

## 7. 这套项目最强的地方在哪里

### 7.1 它把“需求”分成了不同层级

这非常重要，因为很多系统失败是因为把所有问题混在一起问。

它把问题分成：
- 产品问题
- 需求问题
- 规则问题
- 工程问题
- 实施问题
- 测试问题

### 7.2 它把每一层都写成可交付文件

这意味着每一层都可以保存、审查、再利用。

### 7.3 它对依赖关系非常敏感

特别是 RFC 顺序和 change management。

### 7.4 它适合和 AI 合作

因为它减少了：
- 上下文混乱
- 幻觉
- 自由发挥
- 无边界实现

## 8. 这套参考的局限性

### 8.1 它偏重文档链，而非自动执行

它强在“文档驱动”，不强在“一键执行”。

### 8.2 它默认用户愿意维护较完整的文档

如果用户不愿意写/看文档，效果会打折。

### 8.3 它依赖高质量输入

如果 PRD 起点很差，后续产物都会偏。

### 8.4 它更适合中大型项目

对于非常简单的任务，这套流程可能显得重。

## 9. 对你当前系统的直接启示

你的系统现在已经有：
- 版本管理
- 阶段管理
- 问题数量控制
- 文件生成
- 锁定/归档

这说明你已经有“工作流壳子”了。

但如果要向这个参考靠拢，还需要补：

### 9.1 明确目标模式
至少区分：
- PRD 模式
- 验证模式
- Features 模式
- Rules 模式
- RFC 模式

### 9.2 明确每一轮输出工件
不要只是聊天，要明确每个阶段最终生成什么。

### 9.3 明确输入输出协议
每个阶段都需要明确：
- 输入是什么
- 期望产出是什么
- 不足怎么办
- 格式不对怎么办

### 9.4 明确工件传递链
上游文档要成为下游 prompt 的输入。

### 9.5 明确质量门槛
每一层都要有验证标准，而不是只生成不检查。

## 10. 如果把它抽象成一个可迁移框架

你可以把这套参考抽象成 8 个问题：

1. 当前阶段是什么？
2. 当前阶段的输入是什么？
3. 当前阶段要产出什么文件？
4. 当前阶段需要问哪些问题？
5. 哪些问题必须先问？
6. 哪些问题可以后置？
7. 什么条件下可以进入下一阶段？
8. 如果信息不足，是否继续问或回退？

这 8 个问题本质上就是一个 AI 工作流内核。

## 11. 可直接复用的设计思想

### 11.1 文档优先

先定义文档，再定义实现。

### 11.2 产物优先

每个阶段都必须有产物，不允许只聊天。

### 11.3 依赖优先

后置工件必须依赖前置工件。

### 11.4 校验优先

生成后要验证，不要默认正确。

### 11.5 变更治理优先

需求变动必须通过变更流程处理。

## 13. 最终总结

`ai-prd-workflow-main` 不是一个普通的 prompt 集合，而是一个 **以 PRD 为核心、向下派生 Features / Rules / RFC / Implementation / Review / Testing 的完整工程工作流系统**。

它最重要的价值不在于“AI 能问多少问题”，而在于：

- 每个阶段都问对该阶段该问的问题
- 每个阶段都产出可传递的文档
- 每个阶段都为下一个阶段提供上下文
- 每个阶段都设有质量门槛和依赖边界

如果你要把你当前的系统升级到这个层次，核心不是“增加更多随机问题”，而是要把你的内核改造成：

> **阶段明确、目标明确、产物明确、依赖明确、校验明确的文档驱动工作流。**
