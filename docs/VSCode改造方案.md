# VS Code 改造方案

## 1. 文档目的

本文档说明如何参考 `vscode-main` 的源码结构与视觉逻辑，裁剪并改造成当前项目所需的工作台 App 形态。它重点回答：**哪些结构可以借鉴、哪些要保留、哪些要改成我们自己的东西、怎样避免直接复制造成后续维护困难。**

---

## 2. 基本原则

### 2.1 可以借鉴，但不整套搬

- 可以借鉴 VS Code 的布局骨架。
- 可以借鉴 Explorer、Editor、Panel、Tab、Status Bar 的组织方式。
- 可以借鉴编辑器的行号、行高、选中行、滚动、密度、边框节奏。
- 不建议直接把完整源码或完整 UI 逻辑搬过来。

### 2.2 先结构，后功能

- 先借鉴布局结构。
- 再借鉴视觉尺度。
- 再借鉴交互节奏。
- 最后才考虑功能复用。

### 2.3 先裁剪，再改造

- VS Code 很大，不能按“全量接入”思路处理。
- 必须先裁剪掉当前不需要的部分。
- 保留未来可能会用的结构，但不在第一阶段实现。

---

## 3. 我们要借鉴的 VS Code 核心模块

### 3.1 工作台布局

可借鉴点：
- 顶栏 + 左侧栏 + 主编辑区 + 侧边面板
- 分栏节奏
- 边界线层级
- 面板密度
- 统一暗色主题

用途：
- 作为当前 app 的整体结构参考。

### 3.2 Explorer

可借鉴点：
- 文件树层级
- 文件项密度
- 当前项高亮
- 文件组标题行
- 图标/状态点

用途：
- 作为左侧文件栏的视觉和结构参考。

### 3.3 Editor

可借鉴点：
- 行号
- 当前行高亮
- 行距与字号
- 滚动容器的处理
- 代码区密度控制
- 选中态与内容绑定

用途：
- 作为中间 Markdown 编辑器的实现参考。

### 3.4 Title / Tabs / Status 信息区域

可借鉴点：
- 标签式切换
- 版本/文件切换的节奏
- 状态提示的排布方式

用途：
- 作为顶部版本栏和局部状态栏的参考。

### 3.5 Panel

可借鉴点：
- 面板区信息密度
- 输入区和消息区分层
- 工具与内容的分隔

用途：
- 作为右侧 AI Chat 面板参考。

## 4. 不直接搬的内容

以下内容当前不直接引入：

- 终端系统
- Debug 系统
- 完整 Git SCM 面板
- 扩展市场
- 完整设置中心
- 复杂命令中心
- 远程/容器/SSH UI
- 多编辑器复杂分屏
- minimap
- 自动补全与提示系统
- hover、inline hint、参数提示完整能力

原因：这些内容会让项目复杂度显著上升，而当前目标是一个专注的文档工作台。

## 5. 改造策略

### 5.1 布局改造

目标布局：

- 顶部：版本栏
- 左侧：文件栏
- 中间：Markdown 编辑器
- 右侧：AI Chat

改造要求：
- 使用统一的栅格或 flex 布局。
- 所有栏位高度和边框节奏统一。
- 避免多个区域各自定义高度，导致视觉断裂。

### 5.2 编辑器改造

目标：让编辑器像真正编辑器，而不是装饰性文本区。

改造要求：
- 行级结构必须明确。
- 当前行高亮必须绑定到具体文本行。
- 滚动后高亮不能丢。
- 行高必须和字号、内边距同步。
- 光标、当前行、行号必须保持统一节奏。

### 5.3 Explorer 改造

目标：左侧文件栏既像 Explorer，又是你的项目文档导航器。

改造要求：
- 只保留项目相关文件。
- 文件层级要清晰。
- 当前文件必须突出。
- 可以有状态点，但不要花哨。

### 5.4 Chat 改造

目标：右侧 Chat 面板服务于文档推进。

改造要求：
- 信息密度克制。
- 用户气泡与 AI 气泡风格统一但有区分。
- 输入框和提示区要简洁。
- 不要像完整聊天 App。

### 5.5 版本栏改造

目标：顶部版本栏是版本切换和状态表达，不是普通标签页。

改造要求：
- 版本选中态必须统一。
- 版本栏高度与其他栏标题行一致。
- 版本信息要能表达冻结、当前、派生等状态。

## 6. 如何使用当前 HTML

### 6.1 当前 HTML 的定位

当前 `preview/ide-md-chat.html` 是原型页，不是最终实现。

它的职责：
- 快速验证布局和视觉风格
- 快速试验编辑器、版本栏、文件栏、Chat 的一致性
- 快速观察滚动、选中、高亮、气泡、间距等问题

它不承担：
- 最终组件化架构
- 最终数据流架构
- 最终版本管理逻辑
- 最终文档治理逻辑

### 6.2 当前 HTML 的正确使用方式

#### 第一步：先作为视觉原型

- 用它验证四栏布局是否合理。
- 用它验证样式变量是否统一。
- 用它验证编辑器高亮、滚动和气泡是否自然。

#### 第二步：逐步抽离公共样式

- 把重复的颜色、间距、边框、圆角提炼成公共变量。
- 把标题行、文件项、消息气泡提炼成复用 class。

#### 第三步：再拆成组件

- 顶部版本栏组件
- 左侧文件栏组件
- 编辑器组件
- Chat 组件
- 状态提示组件

### 6.3 当前 HTML 不应长期承担的事情

- 不应长期承载复杂状态逻辑。
- 不应长期承担所有文档内容。
- 不应长期靠手写绝对定位去模拟编辑器行为。
- 不应把所有页面细节都写死在一个文件里。

---

## 7. 当前 HTML 到正式 App 的迁移路径

### 7.1 阶段 A：保留原型页

保留 `ide-md-chat.html` 作为视觉对照。

### 7.2 阶段 B：抽样式变量

把公共样式抽成统一主题变量，例如：
- 背景色
- 面板色
- 边框色
- 主文字色
- 次文字色
- 选中态色
- 间距
- 圆角
- 字号

### 7.3 阶段 C：抽结构组件

把左、中、右、顶部拆成独立模块。

### 7.4 阶段 D：抽数据模型

把版本、文件、日志、差异、归档抽成明确数据结构。

### 7.5 阶段 E：替换静态模拟

把静态内容逐步替换成真实数据渲染。

---

## 8. 从 VS Code 借鉴后的保留/删减策略

### 8.1 建议保留

- Explorer 结构
- Editor 行级逻辑
- Tab / Version 逻辑
- Panel 布局
- 状态栏的思路

### 8.2 建议暂缓

- complex debug/terminal/extension 架构
- 完整命令中心
- 高级编辑器能力

### 8.3 建议改造

- 版本栏替代普通 tab
- 文件栏替代通用 Explorer
- AI Chat 替代普通 Panel
- Markdown 编辑器替代 code editor 但保留行级感

---

## 9. 风险控制

### 9.1 不要被 VS Code 的规模带偏

VS Code 复杂度很高，不等于我们要复制其复杂度。

### 9.2 不要用静态浮层长期冒充编辑器能力

当前看到的选中行问题，本质上就是“模拟层”不稳定。正式版本必须用结构化行渲染解决。

### 9.3 不要过早引入不必要能力

当前最重要的是把工作台做稳，不是把所有 IDE 能力一次性做齐。

---

## 10. 结论

VS Code 适合作为骨架参考，不适合作为整包搬运目标。

正确路径是：

- 借布局
- 借节奏
- 借层级
- 借编辑器行逻辑
- 不借全量复杂度

当前 HTML 是原型起点，后续应逐步演进为组件化、数据化、文档化的正式 App。
