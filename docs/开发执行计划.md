# 开发执行计划

## 1. 文档目的

本文档用于指导具体开发执行。它回答三个问题：

1. 现在要先做什么
2. 每一步做到什么程度算完成
3. 哪些问题必须先解决，哪些可以后置

本文档面向开发执行，不面向产品宣传。

---

## 2. 开发目标

### 2.1 本阶段目标

把当前静态页面改造成一个可持续迭代的 App 原型，并逐步演进为正式工作台。

### 2.2 当前阶段必须完成的结果

- 整体页面结构稳定
- 左中右三栏职责明确
- 顶部版本栏与其他栏风格统一
- 编辑器的当前行高亮稳定
- 右侧 Chat 气泡和输入区统一
- 样式具有复用性
- 后续能拆组件、拆文档、拆数据结构

---

## 3. 开发范围

### 3.1 当前必须做

- 统一页面骨架
- 修复编辑器高亮逻辑
- 统一版本栏 / 文件栏 / Chat 栏样式
- 抽取公共样式变量
- 建立文档体系
- 建立版本、日志、差异、归档的文件结构

### 3.2 当前可暂缓

- 终端
- Debug
- 完整命令中心
- 复杂搜索替换
- 高级补全/hover/minimap
- 复杂拖拽调整面板宽度

### 3.3 当前不要做

- 不要重写完整 VS Code
- 不要全量接入编辑器生态
- 不要在单个 HTML 里堆所有逻辑

---

## 4. 开发顺序

### 阶段 0：整理文件

#### 目标
建立开发文档、总纲文档、改造文档、执行文档的基本文件体系。

#### 交付物
- `APP改造总纲.md`
- `VSCode改造方案.md`
- `开发执行计划.md`
- `产品推进路线图.md`
- `文档与目录规范.md`

#### 完成标准
- 每份文档职责清晰
- 不重叠，不互相抢职责

### 阶段 1：统一页面骨架

#### 目标
让页面看起来是一个整体，而不是拼接页。

#### 任务
- 统一顶部、左侧、中间、右侧高度节奏
- 统一颜色、边框、圆角、间距
- 抽出公共变量和公共 class
- 修复右侧气泡视觉偏差

#### 完成标准
- 四个区域视觉一致
- 没有明显“各写各的样式”痕迹

### 阶段 2：修复编辑器行级结构

#### 目标
解决当前“选中行不稳定”的根因。

#### 任务
- 把选中行从浮层式模拟改成行级结构
- 让行高、字号、padding 对齐
- 滚动后高亮不丢失
- 顶部渐变和当前行高亮逻辑分离

#### 完成标准
- 选中行始终跟随真实内容行
- 滚动后高亮仍然存在
- 不依赖静态 overlay 去冒充编辑器行为

### 阶段 3：抽离静态内容

#### 目标
把当前 HTML 中的硬编码内容拆成可配置内容。

#### 任务
- 文件列表数据化
- 版本栏数据化
- Chat 消息数据化
- 编辑区正文数据化

#### 完成标准
- 页面内容可由数据渲染
- 不再直接依赖手写静态块

### 阶段 4：组件化

#### 目标
把页面拆成可维护组件。

#### 组件建议
- `TopVersionBar`
- `FileExplorer`
- `MarkdownEditor`
- `ChatPanel`
- `StatusBar`

#### 完成标准
- 每个组件职责单一
- 样式和逻辑可独立维护

### 阶段 5：文档治理能力

#### 目标
让 app 真正能管理版本与文档。

#### 任务
- 版本生成
- 版本冻结
- 版本差异
- 确认记录
- 问答记录
- 归档索引

#### 完成标准
- 用户可以回看历史版本
- 可以追踪修改原因
- 可以冻结并归档

---

## 5. 每个模块的实现要求

### 5.1 顶部版本栏

- 高度固定
- 选中态统一
- 状态清晰
- 版本切换不依赖复杂交互

### 5.2 左侧文件栏

- 结构清晰
- 文件项密度一致
- 选中态明确
- 可预留目录和状态标识

### 5.3 中间编辑器

- 真正按行渲染
- 当前行高亮稳定
- 需支持滚动
- 不能用单个固定 overlay 假装选中态

### 5.4 右侧 Chat

- 消息密度克制
- 气泡颜色统一主题
- 输入区清晰
- 作为辅助面板，不喧宾夺主

---

## 6. 样式复用要求

### 6.1 必须复用的公共变量

至少包括：
- 背景色
- 面板色
- 面板软色
- 线条色
- 主文本色
- 次文本色
- 强调色
- 成功色
- 提示色
- 失败色
- 字体变量
- 圆角变量
- 间距变量

### 6.2 必须复用的公共 class 类型

- 面板头部样式
- 标签样式
- 选中态样式
- 气泡样式
- 文件项样式
- 文本次级样式
- 状态标记样式

---

## 7. 开发验证方式

### 7.1 视觉验证

检查：
- 是否统一
- 是否有明显错位
- 是否有高度不一致
- 是否有重复定义的样式

### 7.2 交互验证

检查：
- 编辑器滚动后高亮是否还在
- 版本栏选中是否正常
- 文件栏选中是否正常
- Chat 气泡是否统一

### 7.3 结构验证

检查：
- 页面是否组件化
- 数据是否已从静态硬编码中抽离
- 文档是否已经形成总纲 + 方案 + 执行 + 路线图的结构

## 10. 风险点

- 静态页面改造为组件时，结构可能重排
- 编辑器行级结构改造时，可能引入新的行高问题
- 文档体系建立后，若命名不统一，会增加维护成本
- 过早删除内容会导致后续返工

---

## 11. 结论

本计划的核心不是一次性做完全部功能，而是先建立稳定的开发秩序：

- 有总纲
- 有改造方案
- 有执行计划
- 有产品路线
- 有文档规范
- 有清晰分阶段目标

这样后续开发才不会再靠临时判断。
