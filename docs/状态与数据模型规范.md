# 状态与数据模型规范

## 1. 文档目的

本文档定义当前 App 中涉及的版本、文件、编辑器、Chat、日志、差异、归档等状态如何建模、如何流转、如何引用。

---

## 2. 设计目标

- 状态要明确
- 数据要可追踪
- 结构要可扩展
- 静态原型能平滑过渡到动态实现
- 版本、文件、内容、日志、差异之间关系要清楚

---

## 3. 核心实体

### 3.1 版本实体

版本代表某一时刻的稳定结果。

```ts
interface VersionItem {
  id: string;
  title: string;
  status: 'draft' | 'collecting' | 'refining' | 'confirmed' | 'frozen' | 'archived';
  createdAt: string;
  updatedAt?: string;
  active?: boolean;
}
```

### 3.2 文件实体

文件代表项目中的文档、日志、差异或目录项。

```ts
interface FileItem {
  id: string;
  name: string;
  type: 'folder' | 'md' | 'json' | 'log' | 'diff';
  status?: 'normal' | 'draft' | 'frozen' | 'archived';
  active?: boolean;
  parentId?: string | null;
}
```

### 3.3 编辑器行实体

编辑器按行组织。

```ts
interface EditorLine {
  id: string;
  lineNumber: number;
  text: string;
  type?: 'heading' | 'paragraph' | 'list' | 'code' | 'quote' | 'meta';
  active?: boolean;
}
```

### 3.4 消息实体

Chat 由消息组成。

```ts
interface ChatMessage {
  id: string;
  role: 'user' | 'assistant';
  content: string;
  createdAt: string;
  status?: 'sending' | 'sent' | 'failed';
}
```

### 3.5 Chat 上下文实体

```ts
interface ChatContext {
  documentName: string;
  versionId: string;
  versionStatus: VersionItem['status'];
  stage: 'layout' | 'editor' | 'chat' | 'versioning' | 'archive';
  pendingItems?: string[];
}
```

---

## 4. 状态流转

### 4.1 版本状态流转

`draft -> collecting -> refining -> confirmed -> frozen -> archived`

### 4.2 文件状态流转

`normal -> draft -> frozen -> archived`

### 4.3 消息状态流转

`sending -> sent` 或 `sending -> failed`

---

## 5. 状态字段使用原则

### 5.1 active 的使用

`active` 只表示当前选中项，不表示冻结、不表示确认。

### 5.2 status 的使用

`status` 表示生命周期状态。

### 5.3 parentId 的使用

用于描述文件树层级，避免将目录结构写死在 UI 里。

---

## 6. 数据引用原则

### 6.1 版本优先

UI 的当前状态应优先从版本数据派生。

### 6.2 文件跟随版本

文件列表与版本状态要能关联，但不能互相混淆。

### 6.3 编辑器内容跟随文件

编辑器显示内容应来自当前文件。

### 6.4 Chat 跟随上下文

Chat 消息应能知道当前文档、当前版本、当前阶段。

---

## 7. 推荐的状态组合

### 7.1 页面全局状态

```ts
interface AppState {
  activeVersionId: string;
  activeFileId: string;
  activeLineId: string;
  messages: ChatMessage[];
  versions: VersionItem[];
  files: FileItem[];
  lines: EditorLine[];
  chatContext: ChatContext;
}
```

### 7.2 当前选中逻辑

- 当前版本由 `activeVersionId` 决定
- 当前文件由 `activeFileId` 决定
- 当前行由 `activeLineId` 决定
- 当前 Chat 文本由 `messages` 决定

---

## 8. 数据与 UI 的分界

### 8.1 数据层负责

- 提供版本、文件、消息、行数据
- 提供状态流转
- 提供上下文引用

### 8.2 UI 层负责

- 渲染数据
- 展示选中态
- 响应用户操作
- 发出状态变更请求

### 8.3 不允许的情况

- UI 直接硬编码大量业务数据
- 组件内部互相复制状态
- 一个区域偷偷管理另一个区域的核心状态

---

## 9. 状态命名规则

- 版本状态命名必须统一
- 文件状态命名必须统一
- 编辑器行状态命名必须统一
- Chat 上下文命名必须统一

不要同时出现多个同义但不同写法的状态名。

---

## 10. 数据演进建议

### 第一阶段

全部先用静态数据渲染。

### 第二阶段

把静态数据变成配置文件或本地数据对象。

### 第三阶段

把数据接入真实状态管理。

### 第四阶段

再加版本持久化、日志持久化和归档持久化。

---

## 11. 验收标准

状态与数据模型规范完成后，应满足：

- 各模块都有清晰的数据结构
- 状态能描述生命周期
- 页面能由数据驱动
- UI 和数据分层明确
- 后续扩展不需要推翻重来

---

## 12. 结论

状态模型不是形式化装饰，而是后续一切功能稳定演进的基础。

先把状态定义清楚，后面改代码才不会乱。
